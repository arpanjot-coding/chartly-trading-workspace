# P06 paper storage, journal and report integration

3 November 2026. Implementation notes; package completion is controlled by root's integrated/browser acceptance. The existing original journal tabs and chart UI remain the presentation base. [Ordered plan](IMPLEMENTATION_PLAN.md), [canonical handoff](../../../../contracts/v1/HANDOFF_SEQUENCES.md).

## Durable transaction boundary

`database/paper_sessions_db.py` registers `workspace_paper_sessions` on the existing workspace metadata before the local engine is created. Its primary key is authenticated principal + source origin + numeric legacy run ID. A deferred foreign key retains the real parent practice run. A row holds the pinned engine/configuration/manifest, authoritative financial state and complete bounded command receipts/ledger/checkpoint. It does not hold credentials, source code or market-data files.

`PaperRecords(storage)` accepts a caller-owned connection for `load`, `list` and `save`. It never opens its own connection, thread, stream or worker. Root's run service commits its row with `JournalService._save`, run marker and receipt in the same existing SQLite transaction. A failure before commit leaves the previous account, journal and checkpoint intact. The stored engine checksum and sequence are checked against the canonical checkpoint; engine restore validation independently reconciles cash, fees, positions, fills and command/order ledger relationships.

Limits are 32 MiB per record, 128 MiB total UTF-8 paper payload per source origin, 500 runs and 5,000 request receipts per run. The engine imposes its smaller state/order/position/fill/ledger/active-order/curve budgets. Aggregate save checks use SQL byte lengths instead of selecting every ledger. Known canonical source/owner/account/book scope and parent profile/run references are checked; malformed, duplicate, nonfinite, secret-bearing or inconsistent payloads are rejected.

Routine workspace responses expose only a compact `practiceSessions[].paper` marker and explicitly skip selecting the large paper table. The marker is `{version,revision,status,manifestId,window?,startingCash?}`. Current preparation, branch and resumed publication supply exact decimal-text `startingCash` from the pinned server config. It is protected alongside the managed marker: broad compatibility saves cannot alter it or substitute project-level capital. The journal uses the selected run's verified amount for its baseline/curve. Older summaries without that amount show capital unavailable and direct the user to inspect the pinned account; saving a chart decision does not repair capital provenance. Broad saves also cannot change managed financial/configuration/source/window/status fields. Archive and legitimate review/display fields remain available. Prepared runs get their own empty paper book before any fill exists.

## Confirmed executions into the original journal

`project_paper_positions(state, session, record, at=...)` operates only on the supplied in-memory transaction state. One explicit engine position maps to one journal position in that run's own paper book. The source is `simulator`; its profile/session, instrument, economic unit and immutable manifest/position identity stay attached.

Every confirmed engine fill becomes a validated normalized P03 execution event. Its identity is scoped by stable paper manifest + fill ID; its position key is scoped by manifest + engine position ID. Request retry or repeated projection adds no second trade, execution event, history record or financial revision. A later fill using an existing identity with changed facts is a conflict. Canonical engine units map explicitly to the existing journal vocabulary: share→shares, base_asset→coins, contract→contracts and lot→lots.

Entry fees affect settled cash immediately. The journal records each nonzero entry fee as a zero-quantity `fee` realization; it is not counted as a profitable/loss-making exit sample. Each partial/final exit records its actual closing quantity, execution price, recognized gross P&L and exit fee. Entry costs are not allocated again. Realized totals therefore reconcile to settled cash even when an entry remains open. Closed-trade outcome includes every entry and exit cost exactly once. Full quantity closure retains currency-rounding residues through the engine's cumulative gross settlement, so splitting exits does not discard fractional P&L.

User strategy/setup/notes, review status/revision, review timestamp, chart evidence and archive state are preserved as the engine adds facts. Existing review history retains its reviewed fact revision; the simulator does not pretend a later fill was present during an earlier user review. Financial source facts are locked against the manual trade lifecycle and generic table replacement. Chart captures continue through P05's existing immutable evidence boundary.

Projection also populates the existing journal stop/target fields from the source position's protective levels and retains its originating order reference. The full engine record remains authoritative for exact source values. Distinct paper-book labels include the run identity, and journal/header chart links retain selected run/book/return context. Realized-exit sample statistics are labelled separately from the report's completed-position sample; managed run cards explicitly load authoritative report metrics rather than treating each partial close as a completed position.

## Backup, restore and scoped export

The installed `paper-sessions` backup module travels alongside P02/P03 journal, bindings, images and native layouts. Older archives without it upgrade to an empty paper list; missing required modules or undeclared extra ZIP members still reject. Full preview validates engine state and its checksum, record/run/marker relationship, branch receipt scope and exact source references before committing.

Same-owner restore/Undo preserves the paper record and engine state. Owner-confirmed cross-owner restore deliberately changes local owner/workspace/account/book references using the rebuilt paper-book map. Original manifest identity, dataset IDs/checksum, engine state, request identities and fill provenance remain retained. Existing source IDs resolve only through P04's verified bundle aliases before the run service can resume. The original owner remains unchanged. No restore operation starts playback or sends an order.

The original paper-book JSON export has an additive `paperSessions` field containing only that book's matching durable run records. Manual and connected exports retain their existing shape. Existing run/trade chart images stay in the book's scoped attachment export; candle files still require their separate dataset bundle. Full workspace restore is the supported transactional recovery path; a raw browser snapshot containing a managed paper marker is refused with an action to use the complete workspace archive, preventing marker-only recovery without its ledger.

## Reports and comparisons

`canonical_manifest` and `canonical_checkpoint` create adapters accepted by the shared P01 `RunManifest`/`Checkpoint` validators. The manifest pins the selected source, actual UTC run window/availability horizon, explicit economics/cost model, seed and engine/fill-policy version. The checkpoint binds the exact engine-state SHA-256, sequence and playhead. Report identity is deterministic for the same persisted record.

`build_paper_report` includes those adapters and validated `MetricResult` values, source/checksum, costs/economics/policy, observed coverage, financial summary, actual orders/positions/fills/ledger and chart/journal drilldowns. Open marked P&L remains separate from realized cash. Completed-position win rate/profit factor excludes open positions and fee realizations; empty samples/zero loss denominators are explicitly unavailable. Known account-state totals are one account snapshot, not a fabricated trade sample. Drawdown uses the engine's every-observed-close extrema; a sampled display curve cannot redefine that metric. No annualized ratio or tick/queue accuracy is invented.

`compare_paper_reports` returns independent selected runs, each with its own capital, currency, source window and results. Empty selection means none. It exposes neither pooled equity nor pooled metrics and performs no currency conversion. Root's read-only endpoint resolves owned selections; clients cannot submit report facts to create financial outcomes. Strategy experiments and automated robustness reports remain P21's separate supported engine adapter.

## Focused verification

The focused suites are `test/test_paper_storage.py`, `test/test_paper_journal.py`, `test/test_paper_reports.py` and the independent `test/test_paper_engine_review.py`. They verify actual SQLite scoping/rollback, no ledger SELECT in routine metadata, source/financial locks, aggregate UTF-8 budgets, immediate entry fees, exact partial/final long/short exits, duplicate projection, preserved reviews, matching paper-book export, old-archive upgrade, cross-owner continuation, restore/Undo, P01 adapters, deterministic report checksum and independent mixed-currency comparisons.

Independent engine review found discarded currency residues across partial closes. The engine now recognizes the difference between rounded cumulative exact realized gross and previously recognized gross; six review cases pass for both trade directions and gain/loss half-cents, restored chronology and exception isolation. All helper code is data-only and shares caller-owned transactions. Root records the final integrated/resource/browser proof; these notes do not mark tasks complete themselves.
