Chartly: product and workflow review

Review date: 2 November 2026. Purpose: evaluate the existing app against a free, open-source, local-first journal, charting and deliberate-practice product. This is an assessment and proposed workflow specification; it does not implement the proposed features.

Product conclusion

Chartly has substantial chart infrastructure and a rich journal presentation. Its strongest opportunity is to connect them into one dependable learning loop: bring trade history or market data, study a chart, practise or trade, capture the result, review the decision, and return with a concrete improvement goal.

The current product does not yet complete that loop. Several new profile surfaces describe future connector behavior, while underlying broker tools use a separate global broker/API model. Historical replay is real, but historical paper execution, durable run results and automatic journaling are missing at the integration boundary. The journal can create records and calculate many metrics, but lacks the everyday edit/close/review/recovery lifecycle.

The next milestone should be one excellent, provable end-to-end workflow. Adding more broker names, indicators or analytics panels before that would increase maintenance without resolving the core product gap.

Evidence and limits

  • Ten specialist source reviews cover journal, charts, replay, connections, data/history, execution/risk, navigation/onboarding, research tools, automation/operations, and open-source readiness. Their reports are linked below.
  • Parent browser inspection visited Workspace, the existing live profile, Connections, Journal, and Chart. The current profile has no configured destinations and no trades. The chart opened as an empty plotting area; searching EURUSD returned “No matching symbols”. This observation applies to this local session and data configuration, not all supported brokers.
  • Connections visibly says its account/terminal/source/copy settings are saved locally and that live orders and auto-sync await the connector phase.
  • Source guards for chart and tool routes require authentication and a broker; this browser session nevertheless opens the chart. This is not evidence that a fresh installation can chart without credentials. A separate fresh-session test remains necessary.
  • Existing trader metric/model tests passed: 2 files, 19 tests. The replay specialist ran 4 replay test files: 39 tests passed. The data specialist ran 3 historical-feed/timeframe/interval files: 44 tests passed. Total: 102 tests across 9 files. These are focused component/domain checks, not end-to-end broker or fill-quality certification.
  • No user trades, profiles, connections or settings were created or deleted during this audit. No broker order was submitted. No app implementation was changed.
  • Architecture documents are design intent, not proof that a connector exists or that their market/legal claims are correct. Runtime and source evidence take precedence.

What the product should promise

“Bring your own trading history and market data. Chart, journal, practise and review locally, with optional connections to your own accounts.”

Free software and free market data are separate promises. Users should receive useful journaling without any price feed. Replay needs suitable historical bars or ticks; trade statements alone cannot reconstruct the market. Real-time and historical coverage depend on the chosen provider and the user's access. Do not imply that every asset, venue or depth of history is available free.

Four useful entry journeys

  1. I want to journal: create a workspace → import a statement or add a trade → reconcile → review → inspect patterns. No broker or market-data subscription is required for manual records and journal analytics. Optional chart context requires a suitable dataset.
  2. I want to practise: create a practice project → select/import history → validate coverage → set simulation assumptions → trade historical bars → save/resume → finish and review automatically journaled fills.
  3. I want to chart: choose source and instrument → see available history and freshness → annotate and save layout → attach a chart view to a journal entry. Execution is optional.
  4. I want to connect accounts: choose platform → establish actual connection → verify identity and capabilities → reconcile history → optionally enable one execution destination → demonstrate a demo order lifecycle → optionally configure copying.

All four paths should converge on the same normalized journal and instrument model. None should force a beginner through a broker configuration task that is unrelated to the job they chose.

Keep the domain concepts separate

  • Workspace/profile: organizational scope for strategy, notes, reviews and linked accounts. A profile named “Live” is not evidence of a live connection.
  • Account: one actual execution or imported-history account, with its own currency and external identifiers.
  • Data source: where prices originate, with instrument mapping, coverage, resolution, freshness and provenance. It can exist without an execution destination.
  • Execution destination: an account eligible to receive commands, with verified permissions and capabilities. A configured destination is not a connected account.
  • Dataset: a versioned historical snapshot with timezone, gaps, source, instrument metadata and import validation.
  • Practice run: immutable configuration plus clock/checkpoint, simulator ledger, costs and results. Independent runs are experiments, not automatically one cumulative account.
  • Journal trade: execution facts plus editable decision/review annotations. A master decision can have multiple destination fills; reporting needs an explicit choice between decision-level and account-level views.

Highest-priority workflow gaps

1. Make the journal a durable working record

Current evidence: frontend/src/lib/trader/useTraderData.ts:167 creates trades and :179 deletes them, with no update API. frontend/src/pages/workspace/TraderJournal.tsx:703 is the journal creation caller found in the source review. Browser IndexedDB is the journal's store (frontend/src/lib/trader/db.ts:209).

Build editable trade details, open-to-closed lifecycle, import preview/deduplication, unreviewed queue, attachments, and full backup/restore. Separate factual execution data from a user's later interpretation. Do not treat a filtered CSV report as a complete backup. Surface save failures and preserve drafts; use archive/undo rather than immediate deletion.

Acceptance: import a statement twice without duplicates; correct a trade without recreating it; close an open trade; add a review later; export a full backup and restore all relations and notes into a clean browser or local database.

2. Make data availability a visible product state

Current evidence: the main chart constructs a broker-oriented feed (frontend/src/lib/trading/terminal.ts:7828); replay run sources are disabled in the planning form (frontend/src/pages/workspace/TraderReplay.tsx:273). Selecting a source in profile configuration does not establish a working chart feed. Importantly, Historify already has CSV/Parquet import, durable DuckDB history and a read-only historical feed. Reuse that existing capability; the missing piece is access and integration into the primary journeys, not the basic existence of a candle importer. See the data report for precise implementation references.

Provide a Data library with separate actions for importing market history and importing trade statements. Before any replay, show usable instrument/range/timeframe, timezone, gaps and source limitations. The no-source chart must offer a next action rather than a blank plotting area. Source and execution account remain separate controls.

Acceptance: a user with only a valid candle file can chart and start practice without obtaining an API key; a user with only a trade statement can journal but is clearly told why a market replay needs more data.

3. Bind profile and run context to the terminal

Current evidence: frontend/src/pages/workspace/ProfileShell.tsx:15 puts runId into chart links, while frontend/src/pages/Trading.tsx:1176 uses profile information for navigation without restoring run settings.

Resolve the selected profile/run into verified data, symbol, interval, mode and account configuration. Keep names and URL labels as presentation, not authority. A deep link must either open the intended state or explain exactly what is missing.

Acceptance: two profiles with different sources and two runs with different windows open their own instrument, dataset and simulation state. Invalid or unrelated IDs cannot enable execution.

4. Complete historical paper trading

Current evidence: replay deliberately blocks order actions (frontend/src/lib/trading/terminal.ts:5964; frontend/src/pages/Trading.tsx:634), while sandbox execution uses current quotes (sandbox/execution_engine.py:156). Preserve that live-order block.

Add a simulator driven only by the replay clock, isolated cash/position/order ledger, explicit spread/fees/slippage and same-bar fill policy, saved checkpoint and automatic journal events. Show whether replay uses ticks, lower-timeframe bars or whole-bar steps; do not present OHLC replay as tick-accurate execution. Backward seeking must not silently let a user retain profits while rewinding market state: branch/reset the run or deterministically replay its ledger.

Acceptance: refresh/resume restores a run exactly; identical dataset/configuration/actions produce identical results; future bars are inaccessible to the decision and fill engines; no replay order reaches a broker; finish opens a populated review.

5. Make connection and copying states truthful

Current evidence: frontend/src/pages/workspace/TraderConnections.tsx explicitly describes configuration-only behavior. Its account/terminal toggles are saved intent, not terminal discovery, measured health or acknowledged broker execution.

Use separate labels for Configured, Connecting, Connected read-only, Ready to trade, Armed, Stale and Failed. Start with one reliable read-only connector and history reconciliation; then demo execution; then one live destination; then multi-account fan-out. Show destination-by-destination submitted/acknowledged/partial/filled/rejected/unknown outcomes. Do not automatically retry an unknown outcome as a new trade.

Acceptance: terminal restart, disconnect, duplicate event, partial fill and one-destination rejection have visible, recoverable states. A local “running” checkbox never substitutes for a heartbeat.

Proposed wireframe structure

Keep the black-and-white treatment. The design problem is hierarchy, terminology, state and continuity.

Workspace

Top: workspace identity and three clear actions — Import trades, Start practice, Open chart. Below: recent work and Resume practice; then profiles/projects and a review queue. Account setup is optional and discoverable. Put zero-data metrics behind a small explanation rather than filling the first screen with dozens of zeros.

Chart

Header: profile/project, explicit mode, source and execution target. Toolbar: instrument, timeframe, indicators and layout. Left: drawings. Center: chart. Right: Watchlist / Journal / Objects; specialized tools under Advanced. Bottom: data range/timezone/freshness and either replay transport or account books. Show trade controls only for a valid execution mode. “Attach chart” captures the view directly into the scoped journal.

Journal

Header: profile/account, period, strategy and timezone. Main navigation: Review queue / Trades / Performance / Calendar. Trade drawer: Facts / Decision / Review / Attachments / History. Default view prioritizes unreviewed records and the next useful action. Performance always carries sample size and consistent filtering; optional mindset is separate and explicitly recorded.

Practice project and run

Project: research question, strategy, dataset coverage and comparable runs. Run preparation: dataset → window → cash and instrument economics → costs and fill assumptions → validation → start. Active run: simulated time, paper ticket, position ledger and save status. Finish: execution results, annotated decisions and a next practice goal. Independent runs get comparison statistics, not a fictitious pooled balance.

Connections

Separate source setup from execution setup. Read-only defaults; verify platform/account identity, data and order capabilities, last heartbeat and sync cursor. Destination preview shows exact symbol, side, normalized quantity, stop/target behavior and account before arming. Activity and recovery sit beside configuration. Keep speculative evasion/randomization settings out of the beginner workflow.

Delivery order

  1. Reliable journal: editable records, statement import, full recovery, visible persistence errors and consistent time/metric definitions. This delivers value without solving paid market data.
  2. Offline chart and practice vertical slice: validated imported bars → chart → run-bound simulator → checkpoint → journal → review. This is the strongest demonstration of the free product promise.
  3. Read-only platform connection: one platform, capability discovery, history sync and data provenance using the same normalized objects.
  4. Demo then live execution: one destination, native supported protection, event reconciliation and failure recovery. Expand copying only after the single-destination lifecycle is demonstrably reliable.
  5. Advanced tooling integration: preserve existing options, portfolio research, scripts and automation; expose them through user jobs and capabilities rather than making their full breadth the first-use experience.

These are dependency stages, not time estimates. Completion means the acceptance behavior works, not that all screens have been drawn.

Findings across the remaining app sections

Onboarding, settings and combined analytics

The current first-run split is Live channel versus Replay project (frontend/src/pages/workspace/TraderWorkspace.tsx:523), with no equivalent journal-only job. Its live setup checklist rewards configured destinations, source flags and drawdown flags (TraderProfileDetail.tsx:163), rather than verified runtime readiness. First-run success needs to match the chosen job.

Protect historical meaning when editing profile currency or practice starting capital (TraderProfileDetail.tsx:115). A display-label change must not relabel historical USD values as GBP without conversion. Combined analytics should allow a genuine empty selection rather than interpreting deselect-all as all profiles (CombinedLiveAnalytics.tsx:237); relative periods need actual date bounds. Preserve its existing separation by currency.

Desktop and mobile navigation currently prioritize Workspace / Flow / Tools, while history is in the account menu (frontend/src/config/navigation.ts:32, :79). Promote Data Library, and retain advanced tools through progressive disclosure. Keyboard, responsive navigation and numerous descriptive labels already exist; this audit is not a complete accessibility conformance test.

Portfolio research, options and specialist tools

These are substantive capabilities, not mere placeholders. Coverage includes portfolio/SIP backtesting and holdings analysis; option chains, Greeks, OI tracker/range/profile, max pain, straddle/straddle P&L, volatility surface, GEX, strike profile, gamma density, IV smile, arbitrage, strategy construction and saved strategy portfolios. The tools report inventories each family and its data dependencies.

Local Historify-backed portfolio calculations already exist, but access gates impede their data-independent use. Portfolio/SIP result views are not durable research records; saved option strategies use a separate snapshot store rather than the core journal. Treat each research result as dated evidence with assumptions and a link back to a profile, trade or experiment. Capability-gate venues and instruments rather than implying a default regional exchange is universally available. Do not market these portfolio or specialist simulations as the same thing as discretionary replay-paper trading.

Keep useful advanced depth, but group it by job: study a market, test an investment allocation, build an options structure, automate a verified strategy. The main Tools catalogue currently leads with automation (frontend/src/pages/Tools.tsx:66); that ordering does not match the stated journal/practice priority.

Flow, scripts, alerts, AI, approvals and operations

Flow, Python strategies, strategy runtimes and platform webhooks are genuine operational systems. Their identity is still primarily user/API-key/broker, not the profile/run model (blueprints/flow.py:28; services/flow_executor_service.py:4974). Activation must expose verified account, environment, permissions, approval policy and limits. A profile's saved copy/risk settings must never silently imply control over legacy automation.

Distinguish Read-only/Simulation/Broker mode, Draft/Armed status and Approval-required/Automatic policy. The API configuration falls back to Auto (blueprints/apikey.py:54); users need to see the effective policy where they activate an action. Preserve existing AI trading-disabled defaults and server-side permission checks.

Action Center already has careful conditional approval claims and unknown-send handling (database/action_center_db.py:284; frontend/src/pages/ActionCenter.tsx:78), and the strategy module has acknowledgement repair, partial-fill folding and restart recovery. Reuse those foundations. Approval, submission and fill must have different labels; “approved and executed” fallback wording can overstate an unknown broker outcome (ActionCenter.tsx:285).

Python schedules and older event views use IST conventions (blueprints/python_strategy.py:64), which need explicit timezone/calendar handling for a global product. Admin, health, logs, diagnostics, security, traffic, latency, MCP and developer access remain optional maintenance surfaces. They should be accessible from context when something fails, without becoming prerequisites for a person's first journal entry.

Open-source, installation and maintenance

This checkout has no root LICENSE, README, CONTRIBUTING or SECURITY file. That is a distribution-readiness gap in the material reviewed, not a claim about the upstream project's public repository or a legal conclusion about dependencies. Establish the host project's license and attribution chain before presenting the packaged product as ready for open-source distribution.

Existing installation material still centers on broker/cloud setup and contains incomplete download commands. Publish and test the actual local Windows path for journal/import/practice, with supported runtime versions and a clear start/stop/upgrade process. This audit's server launch needed an interactive terminal because noninteractive Werkzeug startup refused to serve; the end-user launcher should handle local startup reliably rather than requiring terminal knowledge.

Recovery must cover both browser journal/profile records and backend databases/history, with a restore drill. Existing CI and security workflows have breadth, but the inspected browser-test job's Vite startup does not itself establish a complete Flask-backed journey. Add full-stack tests for fresh-start journal → backup/restore and imported history → replay paper → resume → automatic journal. Preserve current unit tests while testing the missing seams.

Keep one supported capability matrix: implemented, experimental or planned; platform/OS; data/history; read-only/account sync; demo/live execution; protection and reconnect behavior; last tested version. Vendor documentation in this checkout has version drift, and architecture plans exceed shipped bridge capabilities. A narrow set of verified connectors and a strong adapter contract is more maintainable than a large catalogue of unverified platform promises.

Platform feasibility checked against vendor documentation

MT5 officially exposes Python IPC with the terminal, historical bars/ticks, account information and order_send: MQL5 Python integration, order_send. This supports the proposed local bridge direction; it does not establish that Chartly has implemented it.

NinjaTrader exposes AddOn account order creation and execution events: CreateOrder, Execution reference. cTrader offers distinct live/demo API endpoints and TCP/WebSocket connections: Connection documentation.

The engineering implication is to standardize command/event/capability interfaces while keeping platform adapters separate. Having one market feed does not confer execution access to another account, nor guarantee matching symbols, quantities, prices or fills.

Audit 01 — Journaling workflow and integrity

Source review: 2 November 2026. Scope: TraderJournal.tsx, lib/trader/db.ts, useTraderData.ts, metrics.ts, existing metrics tests and repository searches for journal writers. This is a source audit, not a claim of browser-tested behavior. No application code or personal records were changed.

Assessment

The journal has a substantial analytical presentation already: Overview, Trades, Calendar, Breakdown and optional Mind; profile isolation; manual execution fields; per-trade notes; daily state; CSV export; strategy and time filters. It correctly distinguishes cumulative live journal P&L from broker equity, and correctly excludes open trades from realized analytics. The central missing product loop is capture → reconcile → enrich → review → learn. Today the implemented loop is primarily create a manual record → browse analytics → delete it. This matters more to credibility than further metric density or visual polish.

Five highest-priority findings

1. A saved trade cannot be corrected, closed or enriched

Evidence: frontend/src/lib/trader/useTraderData.ts:167 provides createTrade; :179 provides deleteTrade; the returned API at :386 exposes those two, with no trade update operation. In TraderJournal.tsx:1948 onwards expanded rows are read-only; the action at :1996 immediately deletes. :682–759 is an add-only form. The result selector offers Open, yet both timestamps are required (:2106, :2110), and every trade receives a close date (:707).

Impact: a user cannot correct a typo, attach post-session review notes or close a manually logged open trade without deleting and rebuilding it. An excellent journaling system must support review after execution. A completed form is not the end of a trade's lifecycle.

Recommendation: separate immutable execution facts from editable review fields; add a trade detail drawer with Execution, Review and History; allow open trades to have no close date; explicit Close trade action; track revisions for imported facts. Use an Unreviewed queue with a clear next action.

2. Journal ingestion is manual; connector/replay origins are schema plans

Evidence: db.ts:41 declares origins manual/replay/chart/simulator/connector/imported and :94–98 includes external IDs. Repository searches found TraderJournal.tsx:703 as the only data.createTrade call and useTraderData.ts:169 as the only non-test journalTrades.add writer. Trade log copy explicitly says connectors are future (TraderJournal.tsx:1870). There is CSV export (:321) but no journal statement/CSV import flow in the reviewed frontend. :739 labels any manual entry in a replay profile as replay, even if it was not produced by a replay engine.

Impact: a person with hundreds of existing trades cannot receive the intended free journal value without laborious manual reconstruction. A replay-origin label currently identifies profile context, not verified execution provenance.

Recommendation: prioritize statement import as a free, data-independent first-class route. Flow: choose account/profile → upload CSV → map columns/timezone/currency → preview normalized trades and errors → deduplicate → commit → review import summary. Connect broker/terminal events to exactly the same normalization path later. Distinguish manual provenance from replay session context.

3. Browser-local storage has no complete recovery path

Evidence: db.ts:209 creates the named Dexie IndexedDB; useTraderData.ts:58–96 loads browser tables, with no server journal persistence. TraderJournal.tsx:321–363 exports selected filtered trade columns only. It omits technical/emotional/other notes, detailed emotion scores, plan checks, session ID, account linkage, timeframe, daily states and profile metadata. No complete journal backup/restore route was found. :1996 deletes without confirmation or undo, as does daily-state deletion at :1849.

Impact: clearing site data, changing browser profile or moving between origins such as localhost and 127.0.0.1 can make the journal unavailable. CSV is a useful report but cannot restore the user's complete work. A misclick can permanently remove a review record.

Recommendation: retain local-first operation but persist an authoritative local backend journal or provide versioned full-workspace backup/restore immediately. Show storage location and last successful backup. Offer Export report separately from Backup all data. Add soft delete/Undo with a recoverable trash. Never describe the current CSV as a backup.

4. Time, filters and scoring need stronger semantics

Evidence: TraderJournal.tsx:74–76 formats form input in browser local time; :696–697 converts it to UTC; :79–80 slices UTC dates for daily grouping; metrics.ts:158–160 also slices timestamps. Closing-hour/weekday breakdowns explicitly use UTC (TraderJournal.tsx:500–507), while labels use browser local time (:107–110). TraderPortfolio.timezone exists (db.ts:14) but is not applied in the journal. The 1W/1M/3M cutoff anchors to the latest closed trade rather than today (TraderJournal.tsx:452–464), so a stale journal still shows old trades in 1W. Mind aggregates use all profile records (:476) rather than the period/strategy selection; mood lists are likewise unfiltered (:466).

Metric integrity: metrics.ts:329–343 scores duration according to arbitrary fixed thresholds, giving 5–240 minute trades the maximum score and penalizing scalps and longer holds regardless of strategy. The overall qualitative label is computed from that heuristic (TraderJournal.tsx:132–140). Sharpe/Sortino (metrics.ts:259–283) annualize only days containing trades by sqrt(252), which is not a consistently sampled daily equity-return series, especially for crypto. Global win rate excludes break-even trades (metrics.ts:294), while symbol side percentages divide by all side trades (TraderJournal.tsx:1717–1721).

Recommendation: one profile trading timezone and optional exchange timezone, visible in the global scope bar; standard period dates anchored to today, with a separate explicit Latest activity window; consistent filters across tabs or explicit scope labels; explain win-rate denominator everywhere. Replace evaluative score with transparent metric facts or strategy-specific goals. Label ratios as estimates until cashflows and complete daily returns are modeled.

5. Default and failure states can undermine record trust

Evidence: manual form defaults include EURUSD, Breakout, 1 lot, $100 risk, R:R 2, stop 10 and target 20 (TraderJournal.tsx:397–412), and both plan/risk booleans start true (:417–418). They are saved as facts (:714–720, :735, :742–743). Opting into a mindset check-in saves all four after-trade scores, each initially 3, even when the user never expands the optional after-trade section (:419–422, :744, :2223). useTraderData.ts:88 captures loading errors, but the journal does not render data.error; TraderJournal.tsx:667 can instead present a profile-not-found state after a storage failure. Save/delete handlers do not surface persistence failure and there is no saving guard against double submission (:703, :1996).

Recommendation: blank/unknown defaults for facts, require explicit plan yes/no/not-recorded, and distinguish which optional scores were actually entered. Profile defaults may prefill symbol/timeframe but should be clearly editable. Render actionable storage/save errors, preserve draft contents, disable repeated submission while saving, and confirm successful persistence.

What already works well in the implementation

  • Profile-scoped journal routes and data filtering (TraderJournal.tsx:373–377, :445–448).
  • Manual closed-trade outcome is derived from signed Net P&L (:700–702), reducing common outcome inconsistencies.
  • Optional mindset collection is off unless both profile setting and per-trade consent are enabled (:702, :740–745); historical values are preserved when daily states are overwritten (:777–780).
  • Live broker balance, percentage return and percentage drawdown are not invented from manual records (metrics.ts:213–217, :349–365; tested at metrics.test.ts:71).
  • R-multiple is omitted without positive known risk (metrics.ts:672, test metrics.test.ts:289).
  • Existing metrics tests cover profile isolation, combined live scope, absent emotions, streaks, directions, daily/grouped performance, costs and empty scores (metrics.test.ts:49–294). These tests were inspected, not executed during this audit.
  • Cost and price fields are optional, and the interface explicitly states that entered net P&L remains the analytics value (TraderJournal.tsx:2161). This is honest, though reconciliation warnings should flag gross/cost/net mismatches rather than silently accepting all combinations.

Recommended wireframe structure

Persistent journal header: profile switcher, Live/Replay label, account scope, date interval, strategy/tag filters, trading timezone, data coverage/source status. Primary action Add trades opens a choice of Manual, Import statement and Connect account, with only genuinely implemented routes enabled. Backup state should be one click away.

  1. Overview: compact P&L, realized R, drawdown and sample size; one main equity/P&L chart; Unreviewed trades and Recent imports with next actions. Do not duplicate every Breakdown metric here.
  2. Trades: searchable/filterable ledger; clear status and origin; selecting a trade opens a drawer with execution facts, chart snapshot, setup, plan adherence and notes. Keep unknown facts visibly unknown. Save review without modifying imported execution data.
  3. Calendar: day cells in profile trading timezone → daily detail → review queue. Include daily note even on a no-trade day; current daily summaries only create days with closed trades (metrics.ts:451).
  4. Breakdown: setup/strategy, instrument, direction and session comparisons with sample sizes and net-of-cost expectancy; every cell drills into the exact included trades. Show meaningful minimum samples before ranking an edge.
  5. Mind: optional by profile; separate pre-trade observations from retrospective scores, with explicit recorded sample counts. Do not turn correlations into performance diagnoses.

End-to-end target journeys

Free manual journal: create profile → add execution facts or open trade → persist → return after close → fill review with chart snapshot → weekly review → choose one behavior to practice. No broker or paid market data required.

Statement journal: create account → import statement with timezone/currency mapping → preview duplicates and errors → reconcile totals → approve → review unreviewed trades → export/backup. Future repeated imports must update partial executions without duplicating trades.

Replay learning: choose dataset and date range → create replay session → execute paper orders → events automatically create journal records → finish session → review timeline/chart context → compare repeated runs separately. The reviewed journal currently does not receive this event flow.

Domain requirements before scaling ingestion

  • Normalize execution/deal events separately from a trade aggregate; support partial fills, scale-in/out, fee adjustments and account-specific instrument units.
  • Unique source-event key scoped by provider + connection/account + event ID; externalDealId is currently an ordinary nonunique index (db.ts:222–223), and createTrade has no deduplication (useTraderData.ts:169).
  • Preserve execution currency, account currency and conversion rate/time before combining accounts. The current trade model has no independent currency and simply formats all amounts in profile currency (db.ts:62–110).
  • Store created/updated timestamps, revision provenance and review status on trades; those lifecycle fields are currently absent from JournalTrade.
  • Define deleting a replay session: useTraderData.ts:159–162 removes only the session, leaving journal references; the run breakdown subsequently calls these records Whole profile (TraderJournal.tsx:518–521). Preserve archived session identity or prevent deletion until records are reassigned explicitly.
  • Use reactive subscriptions or cross-tab refresh. The hook loads once and after local actions (useTraderData.ts:94–96); it does not subscribe to other-tab writes, an eventual issue for a chart tab producing journal trades.

Replay, paper trading and backtesting audit

Audit date: 2 November 2026. Scope: source inspection plus targeted automated tests. No broker orders, database mutations, or live account actions were performed. This is a workflow audit, not certification of the third-party simulation engine.

Main conclusion

The app has real chart replay mechanics and a real scripted backtesting integration, but it does not yet deliver historical paper trading as an end-to-end product. Three different concepts sit beside one another: browser-local run planning records, chart-only playback, and a server-side sandbox filled from present-day market quotes. Connecting those is the highest-value work for the stated free journaling and practice promise.

What exists

  • Replay projects have named runs, market, symbol, timeframe, dates, starting balance, editable status and manually linked journal trades (frontend/src/pages/workspace/TraderReplay.tsx:65, :120, :143, :184). Records live in Dexie/IndexedDB (frontend/src/lib/trader/db.ts:31, :200, :212).
  • The project honestly states runs are planning records until a feed is connected (TraderReplay.tsx:124). All actual source choices are currently disabled; the only selectable source is “No data feed connected yet” (:273).
  • Chart replay supports picking a start, play/pause, speeds, step backward/forward, seeking and focused/all-chart scope. A coordinator synchronizes availability times, protects against stale async responses and restores live state (frontend/src/lib/trading/workspaceReplay.ts:69, :145, :205, :277, :380).
  • Chart data is paused during preparation and playback; the terminal uses a displayed prefix rather than the future raw history for legend and volume (frontend/src/lib/trading/terminal.ts:1718, :1949, :5829, :5875). Finer historical candles can form larger candles, with whole-bar fallback when unavailable (:5679, :5838, :6258).
  • Live order entry is deliberately blocked during replay across chart and dock routes (terminal.ts:5964, :5979; frontend/src/pages/Trading.tsx:634). This is a strong existing protection to preserve.
  • Scripted strategies can be compiled and backtested over fetched history, on a worker where supported, with instrument metadata, trades/equity/markers and stopped-run diagnostics (frontend/src/lib/trading/backtestRun.ts:354, :372, :427, :442; frontend/src/lib/trading/backtestFold.ts:73).
  • Server sandbox execution has conditional database fill claims to avoid duplicate fills (sandbox/execution_engine.py:49) and a quote-range consistency check (:96). These are substantive engineering foundations.

Ranked workflow gaps

P0: Historical paper trading has no order ledger tied to the replay clock

The chart's replay mode refuses orders rather than routing them to an isolated historical account (terminal.ts:5964-6015). The sandbox uses current quote/tick events (sandbox/execution_engine.py:156; sandbox/websocket_execution_engine.py:394, :544), and is not driven by the chart playhead. A user therefore cannot currently choose a past date, trade that historical market, and receive automatically recorded fills in the project's journal.

Wireframe requirement: the top strip must show “Historical practice”, project/run name, simulated date/time, source and fidelity. A paper-only ticket beside the chart must show simulated balance, quantity, risk, entry and native simulator stop/target. These tickets must never call a broker route. Closing a position should append one normalized trade automatically, then offer optional annotations.

P0: “Chart” from a run does not open that run

ProfileShell.tsx:15-25 creates a URL with profileId and runId, but the chart page reads the profile only for its back link (Trading.tsx:1176-1184). Searching the chart source shows no consumer of runId. Consequently the run's symbol, timeframe, date window, starting balance and source do not initialize chart replay. The user creates a run and then enters a general chart workspace.

Requirement: a run should resolve its record, validate the source's history coverage, load its symbol/window, initialize the simulator and checkpoint the same run ID. Replace generic “Chart” with “Prepare data” when unavailable, “Start run” when ready and “Resume run” once a checkpoint exists.

P1: Progress and results are not durable run artifacts

PracticeSession stores planning metadata and status, but no playhead, dataset version/hash, simulator ledger, execution settings or checkpoint (db.ts:31-47). Replay exit explicitly warns that the playhead is lost (frontend/src/components/trading/WorkspaceReplayBar.tsx:223). Backtest outcomes reside in React state (frontend/src/components/trading/BacktestPanel.tsx:285) and the backtester returns its report without saving a project/session record (backtestRun.ts:442). Journal association is manual (TraderJournal.tsx:705, :2098).

Requirement: persist immutable run configuration, source coverage, script/version where relevant, fill policy, costs, ledger events and resumable playhead. Offer a clear “Finish and review” action that produces a journal review; a refresh or navigation should not destroy practice progress.

P1: Status can promise readiness or completion without evidence

Statuses are freely changed through a select (TraderReplay.tsx:184-195) and saved verbatim (useTraderData.ts:151-155). Date ordering is not validated; balance coercion replaces zero with the project's default (TraderReplay.tsx:65-85). A “Completed” run can have no data, no execution and no trades.

Requirement: derive readiness from validated data coverage and simulator preparation. Distinguish “planned”, “data needed”, “ready”, “in progress”, “finished”, and “abandoned”; completing a zero-trade observation run should still preserve elapsed coverage and an explicit explanation. Offer edit/duplicate actions for configuration, not deletion/recreation as the practical way to amend it.

P1: Deleting a run leaves journal references behind

useTraderData.ts:159-163 deletes only practiceSessions. Journal records keep their optional sessionId (db.ts:64) and the journal resolves run names by lookup (TraderJournal.tsx:518, :532, :1949). The card's delete action is immediate (TraderReplay.tsx:203-210). Trades can remain while their run context disappears.

Requirement: archive runs by default; retain their provenance for journal records. If permanent deletion is offered, show impacted trade counts and explicitly preserve/detach or delete dependent records inside one transaction.

P1: Independent experiments are combined into a misleading project account

Each run has an independent starting balance, but the project displays a single balance and win rate calculated over all project trades using the project's baseline (TraderReplay.tsx:39-43, :105-109; metrics.ts:178-207). A run card substitutes its own baseline (TraderReplay.tsx:136-140). Combining independent runs into one equity curve can imply a sequential account history that never occurred.

Requirement: the project overview should compare experiments: run count, trade count, expectancy/R, drawdown, sample and date coverage. Keep balance/equity inside each run. Any pooled trade statistics must say “pooled across independent runs”; avoid a project account balance unless runs explicitly share one sequential ledger.

Simulation credibility requirements

These are required design decisions, not claims that the app already satisfies them:

  1. Clearly separate visual replay, historical paper trading, live paper trading, and scripted backtest. Current “Replay / Backtest / Practice” metadata suggests different execution modes while creating the same planning record (TraderReplay.tsx:17, :252).
  2. State fidelity for every run: ticks, bid/ask, smaller candles or displayed OHLC bars. Smaller-candle replay is not tick replay. Whole-bar fallback is intentional but currently quiet (terminal.ts:6258). Display it beside the clock.
  3. Define when a decision becomes executable. Never fill at the same completed candle close using information revealed only by that close unless this is an explicitly selected assumption. Define same-bar stop/target ambiguity and gap behavior.
  4. Use instrument-specific tick size, contract multiplier, quantity units, account currency and FX conversion. The backtester has a documented fallback contract of INR, point value 1 and default tick/lot (backtestRun.ts:181-192); fallback results must remain visibly provisional for international products.
  5. Define spread, fees, swaps/funding, slippage, partial fills and liquidity limits. The current sandbox fills MARKET at ask/bid when present, otherwise LTP (execution_engine.py:520-529), and limit at the limit price on LTP crossing (:531-541). Its WebSocket adapter sets bid and ask equal to LTP (websocket_execution_engine.py:544-548), so it does not simulate spread on that path. Quote consistency is not an age guarantee; its own comment acknowledges missing timestamps (execution_engine.py:108-111).
  6. Use one UTC event clock with a chosen display zone. Availability timing is timezone-aware and handles DST (replayTiming.ts:13, :51), but the replay label formatter hardcodes IST (replayClock.ts:17). The global market/profile timezone should control the displayed clock.
  7. Scrubbing backward must have explicit semantics: observation-only seeking, rollback to checkpoint, or branching into a new experiment. Existing replay supports step-back/seek (workspaceReplay.ts:282-288), but a future paper ledger cannot simply retain fills from the later time.
  8. Verify future isolation for indicators, comparisons, drawings, data exports, watchlists, quote/depth panes and agent context. Prefix ownership and alert pausing are good existing mechanisms, but this review did not certify every secondary surface or the external chart/script package internals.

Proposed end-to-end wireframe workflow

  1. Replay project overview: strategy hypothesis, setup rules, runs list and comparison. Primary action: “New practice run”.
  2. Run setup: market/instrument, dataset source (imported candles, available public source, user's broker history), coverage preview, interval, dates, display zone, initial account and risk/cost model. Source choices should expose actual availability and requirements.
  3. Data check: bar count, first/last timestamp, gaps, fidelity and entitlement/source description. Only then enable “Start”. No broker needed when a usable imported or free dataset exists.
  4. Practice workspace: persistent project/run breadcrumb, simulated time/fidelity strip, chart, paper ticket, positions/orders, fills and compact journal note drawer. Keep play/pause/step near the chart; never show a live execution destination in the paper ticket.
  5. Pause/resume: autosaved clock, drawings and ledger; resume opens exactly that run. Disclose any dataset revision rather than silently changing past results.
  6. Finish and review: final results, trade list with chart snapshots, rule adherence and notes, automatically stored in this run's journal. Distinguish practice-derived and manually entered outcomes.
  7. Compare: compare independently seeded runs and optionally duplicate configuration into a new instrument/window. Do not sum independent initial balances into an apparent account.

Validation

Executed npm run test:run -- src/lib/trading/workspaceReplay.test.ts src/lib/trading/replayTradingLock.test.ts src/lib/trading/replayTiming.test.ts src/lib/trading/terminalReplayCleanup.test.ts in frontend: 4 files and 39 tests passed. These validate coordinator/lifecycle/lock/timing behaviors; they do not establish realistic historical paper fills, broker connectivity, source entitlements or end-to-end replay-to-journal integration.

First build one complete imported-candle historical practice loop: validated dataset → run initialization → isolated simulator ledger → checkpoint/resume → automatic journal trade → review. Then add source adapters and global instrument metadata. Preserve the existing live-order locks. Scripted backtest persistence and comparable experiments can share the same durable run envelope, with explicit simulator/version provenance.

Review 04 — Connections, market data and desktop platforms

Date: 2 November 2026. Method: read-only source inspection. No broker authentication, live orders, credentials, new accounts or terminal launches were attempted. Recommendations below are design proposals, not implemented behavior. Parent audit separately inspected the running UI.

Verdict

The new profile Connections surface is a useful configuration model, not a connector implementation. Existing broker infrastructure is real, but it belongs to the older API-key/broker architecture. These two systems must be joined through an explicit account-aware backend before profile configuration can determine the chart feed, execution account, synchronized journal or protection state.

What is already good

  • Accounts are reusable identities; terminals and per-profile execution destinations are represented separately (frontend/src/lib/trader/db.ts:134, :152, :168). Browser records contain a secret reference field rather than a password field.
  • New destinations default to copying off (frontend/src/lib/trader/profileModel.ts:183). Disabling an account pauses copying across its destinations (frontend/src/lib/trader/useTraderData.ts:239).
  • Account ownership conflicts across armed profiles are checked transactionally (frontend/src/lib/trader/useTraderData.ts:330; frontend/src/lib/trader/profileModel.ts:134).
  • Risk-increasing setting changes have an explicit classification helper (frontend/src/lib/trader/profileModel.ts:89), and destination fields receive basic validation (:49). This is a useful foundation for a later execution preflight.
  • The page clearly discloses its configuration status (frontend/src/pages/workspace/TraderConnections.tsx:598). That honest disclosure should remain while the system is incomplete.

Five highest-priority gaps

1. Configuration state is presented with operational words

Evidence: TraderConnections.tsx:188 shows “Copy on/off”; :754 shows terminal “On/Off”; :770 updates running and lastSeenAt directly from a browser switch. useTraderData.ts:274 and :284 only write IndexedDB terminal records. profileModel.ts:43 defines active copying as a configuration flag plus account enabled status; it does not require a bridge heartbeat, authenticated session, capabilities or broker acknowledgement. TraderConnections.tsx:598–600 explicitly says live orders and sync await a future phase.

Implication: users can configure an account, mark a terminal “On”, and see “Copy on” without any measured connectivity. The notice prevents a literal claim of implementation, but state labels still teach a false operational model.

Proposal: separate Configured / Verified / Disconnected / Stale / Error status from Trading disabled / Ready / Armed intent. A backend heartbeat should own observed terminal status. A user should never manufacture “last seen” by clicking a switch. Until real connectivity exists, say “Copying configured” and “Terminal registered”.

2. The selected chart source is attached to an execution destination

Evidence: db.ts:175 stores isChartDataSource on ProfileDestination. TraderConnections.tsx:419 resolves it from destinations and suppresses it when the broker account is disabled. profileModel.ts:150 automatically assigns the first eligible destination as source. TraderConnections.tsx:954 presents a selected source as the next step toward charting. In contrast, Trading.tsx:901–923 obtains one global API key and WS URL, shared by all panes, without a profile-source lookup. services/history_service.py:287–300 already distinguishes database history from broker API history, which is a useful lower-level seam.

Implication: the conceptual model makes data access depend on creating an execution destination, even for a user who only wants charts or offline replay. Selecting a source in Connections does not prove the chart uses that source.

Proposal: a first-class Data connection independent of Execution account. A profile chooses public/permitted feed, user-owned historical dataset, or broker-entitled feed. Trading can remain disabled while data stays active. Each chart displays the actual source, instrument identity, freshness and coverage. Missing history should lead to import/download/choose-source actions.

3. MT5/NinjaTrader support exists as a plan and schema, not an adapter

Evidence: TraderConnections.tsx:52–60 lists MT5, NinjaTrader and TradeStation. :734 explicitly calls discovery future work. :471–478 registers paths and account IDs only. Repository searches for MetaTrader5, import MetaTrader, NinjaTrader.Client, canonical PlaceOrderCommand and ExecutionEvent returned no implementation in the inspected Python/C#/TypeScript source. The broker/ directory contains existing Indian brokerage integrations and DeltaExchange; no MT5 or NinjaTrader adapter folder was present. ARCHITECTURE.md:5–12 describes local-first adaptation and canonical schemas to adopt.

Implication: platform names should not be counted as supported integrations. A terminal path is not proof that its account, live data or trading permission is available.

Proposal: connector support registry distinguishing Available / Preview / Planned and capabilities per connector. Build one end-to-end local read-only adapter first: bind terminal → verify account identity → load available symbols → fetch bars/history → sync fills → reconcile journal. Add demo execution only after that loop works. Parent should use current vendor documentation to verify platform-specific transport and restrictions; this review does not assert those from memory.

4. Global broker services do not consume profile destination IDs

Evidence: services/place_order_service.py:27–39 dynamically imports broker modules; :203–221 calls one broker's place_order_api; :367–381 resolves a broker through API key or explicit token/broker. services/history_service.py:312–325 follows the same pattern for history. New browser accounts and destinations are saved through useTraderData.ts:211–220 and :309–357. No connection from these IndexedDB identities to the service calls was found in this scope. frontend/src/stores/brokerStore.ts:3–8 is a global broker manifest with exchange/leverage fields, not per-account execution capabilities.

Implication: profile destinations cannot yet be treated as multi-account order routes. Receiving prices from one account does not establish authority, instrument equivalence or reliable execution on another.

Proposal: backend-owned connection/account IDs; canonical instrument mapping; adapter-specific quantity/tick/lot constraints; idempotent command and event correlation; per-account capability manifest; acknowledged order/fill states. A copy preview should show actual destination symbol, quantity, estimated risk, supported protection and per-account outcome. Reconnect reconciliation must distinguish already-sent commands from new commands.

5. Risk UI is ahead of measurable risk enforcement and overcomplicates setup

Evidence: TraderConnections.tsx:274–290 exposes flat/equity-ratio/smart sizing, unlimited caps when zero, while profileModel.ts:49–85 only validates values. :298–310 exposes randomized delay and lot noise and correctly warns about account rules. db.ts:174–200 stores risk preferences, not observed equity, drawdown basis, symbol contract metadata or a guard enforcement acknowledgement. isDestinationCopyActive does not consult these.

Implication: a checked drawdown guard cannot currently protect an account; “smart” sizing has no visible calculable contract. Advanced behavior creates cognitive load before the trader has verified a connection.

Proposal: start with one instrument, fixed valid size, account identity, current status, native protection capability and explicit armed state. Put advanced policies behind a later section. Show guard status as Not implemented / Configured / Enforced / Triggered, with basis, reset time and action. Do not label a configured cap as active protection. Delay/noise should not be a core product proposition.

Proposed connection wireframe and journey

  1. Choose purpose: “Get chart data”, “Import trade history”, or “Enable execution”. These purposes can share one verified connector but must remain separate permissions/capabilities.
  2. Choose source/platform: list only implemented connections as connectable. Keep planned platforms visibly unavailable. Offer local historical data for practice without an execution account.
  3. Verify: backend discovers terminal or authenticates an API; displays platform, masked account identity, demo/live flag, available markets, current connection and last observed event. A manual identity entry is labelled registration, not connection.
  4. Choose data for this profile: source, symbol mapping, timeframe coverage, freshness and storage availability. “Open chart” is enabled when chart data is ready, regardless of trading being disabled.
  5. Optional destinations: select verified accounts, review per-account size/risk/protection and instrument mapping. Save paused. Simulate the fan-out before live arming.
  6. Operate and recover: compact profile banner shows “Data ready · 2 of 3 accounts ready · trading paused”. Errors have one clear action: reconnect, fix mapping, refresh history or reconcile fills.

Suggested page composition: top connection summary with measured states; main data-source panel; execution destination list; expandable advanced controls; activity/reconciliation log. Reusable account and terminal management belongs in a separate connection library reachable from this page, rather than requiring every beginner to understand three entity types immediately.

Acceptance gates

  • A data-only user opens a populated chart without registering a copying destination.
  • Switching profile data changes the actual history/stream provider and visible source label.
  • Stopping a terminal produces a measured stale/disconnected state; the browser cannot set observed health.
  • Read-only history sync creates deduplicated journal records with account and external-fill provenance.
  • A demo account route accepts one explicit command and displays broker-acknowledged status; retries do not duplicate execution.
  • Multi-account preview shows equivalent instrument/size or blocks unsupported mappings; one failed destination has a clear reconciliable outcome.
  • Configured risk is never presented as enforced risk before a backend confirms enforcement.

Local journal routes deliberately avoid this gate. Historify upload and local chart reading need a local user/session boundary, but neither inherently needs an execution broker. This is a source finding, not a claim that the currently signed-in runtime was observed redirecting.

Recommendation: make Data Library a first-class local surface reachable from profile, chart empty state and replay setup. A user who has a CSV should be able to import and study it without an execution-account prerequisite. Preserve authorization and local access protections while separating them from broker selection.

2. Local-history charts exist but are a separate destination, rather than the profile's usable source

frontend/src/lib/chart/feeds/historifyFeed.ts:132–175 implements a real read-only DataFeed from the local store. It deliberately omits live subscriptions and depth. frontend/src/pages/HistorifyCharts.tsx:110–157 constructs the historical feed and custom-timeframe service; :201–228 resolves catalog deep links to an available interval. :283–304 renders HistorifyChartPane with this feed. Its page has no execution callback by construction, a good separation to retain.

By contrast, profile chart links point to /trading and not this local-data surface (frontend/src/pages/workspace/ProfileShell.tsx:20–29). The run uses a free-text dataSource planning field, not a stable dataset identity (frontend/src/pages/workspace/TraderReplay.tsx:39, :79–92). The chart specialist should own exact Trading run-context wiring conclusions.

Recommendation: one chart shell with a verified source/mode contract. Local historical bars, broker quotes and an optional external provider should be source adapters. Execution is separately Read only / Paper / Broker. A historical dataset must never acquire an order path merely because the user's broker session exists.

3. Import accepts a file but does not provide a trustworthy validation/reconciliation workflow

frontend/src/pages/Historify.tsx:1328–1366 submits the file immediately with symbol, exchange and interval. Its import dialog around :2860 offers no timezone or column mapping. blueprints/historify.py:737–809 limits uploads to CSV/Parquet and 100 MB and uses a unique temporary file, which are useful safeguards.

database/historify_db.py:1672–1768 supports case-insensitive headers and timestamp/date/time/datetime columns, detects milliseconds using the first timestamp, requires volume, coerces OHLC numeric, drops invalid OHLC rows, fills missing/invalid volume with zero, then upserts. It does not show a pre-commit preview, let the user choose timestamp timezone, validate high/low coherence, label missing volume versus zero volume, or show exact row-level errors before committing. Naive datetime strings have no explicit source timezone. Existing data on the same key is overwritten by ON CONFLICT ... DO UPDATE at :694–710.

Recommendation: upload → map columns and timestamp unit/timezone → preview candles → display accepted/rejected rows, duplicates, gaps and overlaps → choose replace/keep/version policy → commit. Do not silently treat unavailable volume as measured zero; support a nullable/unknown semantic where the market or file has no volume. Do not forbid negative prices categorically, since instrument semantics matter.

4. Data keys cannot distinguish sources or immutable replay versions

database/historify_db.py:231–244 keys market_data only by symbol/exchange/interval/timestamp. Catalog :261–271 stores first/last timestamps, count and last download time, but no provider/account entitlement scope, dataset version, import checksum, adjustment basis, price basis or quality report. Two users' or providers' bars under the same symbol key can replace one another; a replay rerun after a data correction cannot establish which version produced its result.

This is a local-first application, so it is not evidence of a deployed multi-user leak. It is a concrete limitation if multiple sources/accounts/users are introduced into the same backend.

Recommendation: Dataset + DatasetVersion identities with source, instrument, account/scope if private, native resolution, timezone/calendar, available range, adjustment/roll basis, imported-at, checksum and validation summary. Pin every replay to an immutable version and record transformation rules. Catalog coverage must include interior gaps, not only min/max/count. Keep private entitled feeds scoped rather than assuming every stored bar is globally shareable.

5. Global-market framing exceeds the current exchange/time conventions

database/historify_db.py:1631–1635 supports Indian exchange codes plus GLOBAL_INDEX and CRYPTO; it does not offer distinct general FX, US equities or futures venue identities. Upload validation rejects other exchanges (services/historify_service.py:924–932). The UI permits only 1m and D storage (frontend/src/pages/Historify.tsx import dialog), while the backend VALID_INTERVALS accepts many native intervals (services/historify_service.py:870–899), so import capabilities are inconsistent.

services/historify_service.py:475–482 turns date windows into timestamps using the host's local timezone. historifyFeed.ts:20–29, :36, :63–70 explicitly compensates by padding a day. Server aggregation has hard-coded IST offsets (database/historify_db.py:1088, :1184). Those conventions may suit the original regional workflow but are not a sufficient global calendar model for FX, crypto, US daylight saving or exchange sessions.

Recommendation: canonical instrument/venue identifiers and source-provided aliases; UTC storage with explicit market/session timezone; instrument calendars; stable daily/weekly bar anchors; validated native interval import rather than forcing all files to 1m/D. Fix server window semantics rather than relying indefinitely on padded queries.

Strengths to preserve

  • Broker history download and local DuckDB persistence already exist (services/historify_service.py:286 onward); local history is more durable than browser-only cache.
  • CSV and Parquet import, sample templates and CSV/TXT/ZIP/Parquet export are implemented.
  • Catalog-derived interval availability prevents opening a 1m-only instrument on an unsupported daily series (HistorifyCharts.tsx:201–228).
  • The local feed is structurally read-only: no live subscription, depth or order callback. This is a sound basis for study and an isolated simulator.
  • Background downloads have job progress, retry, pause/cancel and zombie recovery (services/historify_service.py:1335 onward). These are useful operator tools, best kept behind a simpler user entry.
  • The feed surfaces actionable load errors and preserves request cancellation (historifyFeed.ts:152–170).

Proposed Data Library wireframe

Header: Data Library | Import history | Download from my connection.

Catalog rows: Instrument · Source · Native resolution · Coverage · Quality · Local availability. Each row offers Open chart, Create replay and Export. Optional public/provider feeds can be additional adapters after their actual coverage, limits and permissions are verified. Free application software does not imply universally free live exchange feeds or unlimited history. Do not make a paid feed mandatory for manual journal and imported-history practice.

Audit 06 — Execution, copying and risk credibility

Source review, 2 November 2026. No orders were submitted, credentials read, user records changed or application code edited. This review traces the existing general order path and selected strategy-recovery code; it is not a certification of any broker adapter or a full trading-safety audit.

Assessment

The repository contains real broker execution infrastructure, not merely chart mockups. However, the new profile destination/copy controls are a separate local configuration model that has not been wired into that infrastructure. Treating those controls as operating risk protection or multi-account execution would overstate the current product. The interface already discloses this limitation; preserve and strengthen it.

Price data makes analysis possible. It does not establish authority or ability to trade every other account. Each destination needs its own authenticated connection, tradable instrument mapping, quantity and price rules, permissions, supported order types, margin checks and execution lifecycle. Different accounts can fill at different prices, fill partially, reject, disconnect or remain in an unknown submission state. The product should show this explicitly without burdening the initial journal-only workflow.

Five priorities

1. The destination model does not control the actual execution path

Evidence: frontend/src/pages/workspace/TraderConnections.tsx:598–600 calls this a configuration wireframe and says no live orders or auto-sync run until connectors exist. Saving reports “No connector order was sent” at :171. frontend/src/lib/trader/useTraderData.ts:309–359 validates and persists destinations solely in IndexedDB. Searches of services/, restx_api/ and database/ found no use of ProfileDestination/profileDestinations/copyingEnabled.

The actual generic write path resolves one API key to an auth token and broker (services/place_order_service.py:367–375); database/auth_db.py:1205–1216 selects the current user's auth record and returns its token/broker. Direct internal token/broker calls are also supported (place_order_service.py:379–381). None of that establishes a profile-specific multi-destination router.

Consequence: “Copy on”, “destinations copying” and “Start copying now” (TraderConnections.tsx:189, :576, :882) express saved intent, despite sounding operational. Change their current-build wording to “Copy configured” / “Enable when connected”, or pair the state immediately with “Not executing — connector unavailable”. Later distinguish configured, connected, eligible, armed and actively receiving events.

2. Risk limits are configuration, not server-enforced protection

Evidence: frontend/src/lib/trader/db.ts:173–198 stores sizing, total-lot/position caps and drawdown policy. profileModel.ts:49–85 checks input ranges; :88–132 detects risk-increasing edits; :137–148 prevents one account being armed from another profile. These are valuable configuration safeguards. But no backend consumer of these destination records was found. The account-off check in useTraderData.ts:327 is a browser transaction check, not an execution permission boundary.

Consequence: a displayed drawdown guard cannot yet promise to prevent an order, flatten an account or survive a browser closing. Before enabling connector execution, enforce limits authoritatively at dispatch using current account exposure, reservations for outstanding orders, explicit currency and a defined drawdown baseline/reset timezone. Show whether the policy blocks new entries, cancels pending orders or closes exposure. Avoid describing an emergency action as instantaneous or guaranteed.

3. Multi-account commands need durable per-destination outcomes and uncertain-state handling

Evidence: the general place-order schema (restx_api/schemas.py:22–48) has no client command/idempotency key, profile or account destination ID. The general service dispatches to a broker module at place_order_service.py:221; an exception becomes a generic error at :241–258; a successful acknowledgement returns an order ID at :261–285. This endpoint's interface does not provide durable submission deduplication or an explicit “broker outcome unknown” response. This is narrower than claiming no reconciliation exists anywhere.

Substantial reconciliation does exist in the separate strategy module: append-only acknowledgement repair and exact ownership checks (services/strategy_module/ack_reconciliation.py:57–115), fill-event deduplication (order_events.py:17–26) and cumulative fill folding (:621–689), plus restart recovery (recovery.py:385 onward). Reuse these concepts rather than replacing them with browser retries.

Recommendation: persist a parent intent and per-destination child command before dispatch; use stable deduplication keys and account-scoped external IDs. Keep accepted/working/partial/filled/rejected/cancelled/unknown distinct. A timeout after submission must trigger reconciliation before resubmission. One account's success must not make the whole copy group appear successful. Define the policy for divergence rather than silently retrying into double exposure.

4. Suffix plus multiplier is insufficient instrument and risk normalization

Evidence: ProfileDestination contains symbolSuffixOverride, lotScalingMode, lotScalingFactor and maxLotCap (db.ts:176–180). defaultDestination uses flat scaling 1 (profileModel.ts:187–190). The existing generic schema forbids fractional quantities outside crypto (restx_api/schemas.py:6–18), and uses existing exchange/product conventions (:22–36). That is reasonable for the current broker universe but not a universal MT5 FX-lot or futures-contract model. The broker/ directory currently contains the existing regional and crypto adapter set; no MT5/NinjaTrader/TradeStation adapter directory was present in this review.

Recommendation: resolve a canonical instrument to each destination's native instrument and show contract size, tick size/value, volume minimum/step, currency, expiration and allowed order types. Explicitly convert risk and units; do not silently round a fractional FX lot into integer units or copy one futures contract as one FX lot. Require confirmation of ambiguous mappings and block unsupported instruments. Preview planned quantity and estimated risk per account using destination metadata, with estimates labeled.

5. Broker protection and local automation must be separate concepts

Evidence: existing strategy risk is evaluated on the local tick decision path (services/strategy_module/engine.py:1–11) and dispatched as market exits (order_dispatch.py:45–47). The engine explicitly handles the case where risk fires without broker authorization and records that positions remain open (engine.py:154–176). These are honest recovery mechanisms, but they do not turn a local stop rule into a broker-held protective order. ARCHITECTURE.md adopts native broker-side SL/TP as a planned connector principle; that plan is not proof of implementation.

Recommendation: capability-gate native bracket/OCO/SL/TP in the new connector path and show confirmed broker protection separately from “Chartly-managed exit rule”. A local agent, backend crash, feed outage or expired session affects those two mechanisms differently. Display protective-order acknowledgement and failures per destination. Never reuse a visual stop line as proof that a broker protective order exists.

Proposed monochrome execution wireframe

Keep execution optional. A journal user can ignore this entire surface.

  1. Connection setup: account identity → authenticated/read-only connection → verified capabilities/instrument metadata → optional execution permission. Show terminal/bridge heartbeat and account identity from the actual connection, not a manually toggled “running” flag.
  2. Profile destination list: Account | Connection | Instrument mapping | Sizing | Protection | Armed. Text states, not color alone. An account can be a data source without being an execution destination.
  3. Order preview: intent and source instrument above; per-account rows show native symbol, quantity/unit, order type, price rounding, estimated risk, native protection and eligibility/error reason. Explicitly identify live vs demo vs local simulator.
  4. Activity drawer: one parent intent expands to each destination's command and chronological acknowledgements/fills. Show partial success and unknown outcomes prominently, with reconciliation progress and a clear next action.
  5. Account reconciliation: authoritative broker positions/orders versus Chartly expected state; explain divergences before enabling new copying after reconnect. An emergency action operates on an explicitly identified account scope and reports completion per account.
  6. Journal handoff: append confirmed execution events once; preserve account/provenance IDs and partial fills; keep review annotations editable. Decide explicitly whether profile analytics show the master decision once or each copied account's financial result. Do not count a copied decision as several independent strategy observations without labeling it.

Release acceptance criteria

  • A profile's destination intent is resolved and authorized by the backend; query labels and browser switches cannot pick unauthorized accounts.
  • Retrying the same intent cannot duplicate a destination order. Ambiguous network timeouts stay unknown until reconciled.
  • Rejecting one destination produces a visible partial group outcome and no unrequested rollback trade elsewhere.
  • Partial fill followed by cancellation survives reconnect/restart with correct remaining exposure and journal P&L.
  • Symbol suffix collisions, fractional lot steps, expiry mismatches and incompatible product types block dispatch with actionable errors.
  • Risk checks reserve outstanding exposure and enforce the intended baseline, session timezone and reset behavior.
  • Confirmed broker-held protection remains distinguishable from local automation; unsupported protection cannot be represented as active.
  • Disconnect/reconnect reconciles outstanding orders and positions before copying resumes; disabling copying does not falsely claim existing positions were closed.
  • Replay-paper order intent can never enter the broker write path.
  • Replayed duplicate execution events do not duplicate journal records or performance totals.

What to preserve

Default-off copying, account-off overriding destination settings, risk-change review, single-profile ownership checks, current configuration disclaimers, explicit live/sandbox routing and the strategy module's acknowledgement/fill/recovery work are strong foundations. Build the user workflow on top of them. Defer delay/lot-noise/comment controls from the normal setup path until core correctness is complete; their presence adds complexity without completing connection, execution or journaling.

Verification limits

Static source tracing and scoped repository searches only. No adapter conformance tests, live or demo broker submission, outage experiment or automated test run was performed for this report. Missing wiring describes the inspected profile destination path, not every specialized strategy or order subsystem in the repository.

Audit 07 — Navigation, onboarding and profile workflows

Reviewed 2 November 2026. Source inspection only. No application behavior, settings or user records changed. Runtime observations belong to the parent review; a source guard is not by itself proof of the state of an already authenticated browser.

Assessment

The profile-first reorganization is sensible: Workspace is the home, chart and journal belong to a profile, and replay experiments have their own project type. Most legacy routes remain available rather than being destroyed. However, the navigation still gives global automation greater prominence than the principal learning jobs, while local journals and broker-gated charts/history create a discontinuity. First-use onboarding asks users to classify the infrastructure before it asks what they want to accomplish.

Section inventory

  • Public entry and support: root redirect, FAQ, setup, login, password reset, download, error, rate-limit, not-found, broker authentication (frontend/src/App.tsx:178–193).
  • Local product core: Workspace, combined live analytics, profile overview/settings, journal, connections, replay runs (App.tsx:196–214). TraderLayout has no broker guard (frontend/src/components/layout/Layout.tsx:41).
  • Broker/account books: positions, orders, trades, holdings, search, API key, P&L tracking, leverage, sandbox/analyzer (App.tsx:215–253, :310–312). Layout requires authenticated state and a broker (Layout.tsx:13–20).
  • Research/tools: portfolio/SIP backtesting, holdings analysis, options chain, volatility, OI, Greeks, GEX, straddle, arbitrage, strategy builder/portfolio (App.tsx:233–285). The Tools directory itself is inside the same broker guard (:254).
  • Automation: platform webhooks, Python strategies, Chartink strategies, guided broker strategies, Flow index/editor and approval center (App.tsx:286–309, :335, :357).
  • Advanced operations: admin, quantity freezes, holidays, market timings, diagnostics, MCP, logs, security, traffic, latency, health, account settings, contracts (App.tsx:313–335).
  • Full-width applications: main chart, playground, AI Agent/configuration, Historify/history charts, Flow editor (App.tsx:339–358). These inherit FullWidthLayout's authentication and broker checks (frontend/src/components/layout/FullWidthLayout.tsx:12–18).

Five priorities

1. Onboarding should start with the user's job, not Live versus Replay infrastructure

Evidence: profile creation first asks “What kind of channel is this?” and offers “Live trading channel” or “Replay project” (frontend/src/pages/workspace/TraderWorkspace.tsx:523–563). The live description promises chart-to-destination trading; the replay description calls it one test portfolio. There is no peer “I only want to journal/import my history” choice. The profile overview's setup checklist is destinations, destination-supplied chart data and drawdown guard (frontend/src/pages/workspace/TraderProfileDetail.tsx:159–175). A journal-only user therefore appears unfinished even when they need no connection.

Recommendation: first action choices are Journal my history, Practise a strategy, Explore charts and Connect accounts. Create minimal workspace metadata from that intent; postpone terminal/account/risk concepts. A manual journal should have a successful setup state with no broker. Preserve strict live/practice provenance behind these simpler entry journeys.

Acceptance: on a fresh installation, a person can add or import a trade and reach its review without naming a terminal, enabling copying or buying data. Practice setup explains the required history source before offering Start.

2. Navigation hides a core dependency while elevating advanced automation

Evidence: desktop top-level navigation is Workspace / Flow / Tools (frontend/src/config/navigation.ts:32–36), repeated in mobile bottom navigation (:40–44). History & data is inside the account menu (:79–84). Profile chart links enter /trading, but chart and Historify source routes are guarded by broker authentication while the profile itself is local (App.tsx:196, :339–355). Tools is also guarded, even to browse its directory. useProfileMenuItems filters only leverage, not the other broker-dependent destinations (frontend/src/hooks/useProfileMenuItems.ts:29–32).

Access nuance from parent cross-check: app.py:505–559 can seed a loopback development session with an app user and broker placeholder. Session status can consequently retain app logged-in state without a working broker token. A successful local chart route is therefore not evidence of a verified execution connection. App identity, chosen broker identity and operational connector health need separate state.

Recommendation: make Data Library a first-class product destination. Keep profile context across Journal / Chart / Practice, and place Automation plus research under Advanced/Tools. Route readiness should reflect the specific action's capabilities: viewing local candles does not require an execution broker. Let users inspect useful tools and see contextual requirements before being sent to account setup.

Acceptance: a local candle import is discoverable from Workspace and chart empty state in one decision; it opens historical charts without requiring a broker connection. A restricted action explains its exact prerequisite and returns users to the original task after setup. Validate these in a clean browser session; the current running session may have local guest/session behavior.

3. Profile setup progress confuses configured intent with verified readiness

Evidence: checklist completion is driven by destination count, a selected isChartDataSource flag and a ddGuardEnabled flag (TraderProfileDetail.tsx:163–174), rather than connector health or broker acknowledgements. Creating a live simulator option sets running: true and lastSeenAt: nowIso() locally (TraderWorkspace.tsx:291–313). Replay checklist completion similarly accepts any session with manually stored status Completed (TraderProfileDetail.tsx:187–195).

Recommendation: use separate Configured and Verified states. Configuration completion may say “Source selected”; it must not imply “Receiving data”. Simulator readiness must come from an actual simulator instance. A read-only journal needs a different checklist from a live execution workspace. Show the next task and its dependency, not a universal setup score.

Acceptance: stopping the terminal cannot leave it presented as verified/healthy; a planning run cannot count as an executed/reviewed run; each checklist item names whether it tests saved configuration or observed runtime state.

4. Settings can silently change interpretation of historical records

Evidence: profile save updates currency and replay startingBalance directly (TraderProfileDetail.tsx:115–130). The journal schema holds profile-level currency; historical net P&L numbers are not converted here. Relabeling USD as GBP can therefore relabel prior records without conversion. Timezone/default symbol/timeframe settings are collected (:121–127) but downstream consumers must actually apply them; earlier specialist reviews identify gaps. Save and duplication handlers have no visible error handling in this component (:112–149); loading failure can instead resolve to Profile not found (:91–106). Profile deletion at least asks confirmation (:152–155), a useful protection to preserve.

Recommendation: freeze accounting currency after records exist or provide an explicit migration with original currency/amounts retained and conversion policy explained. Practice capital changes must create a new experiment/version or recalculate a clearly identified run, not rewrite historical assumptions invisibly. Show save-in-progress, saved, failed and retry states; never replace storage errors with not-found messaging.

Acceptance: changing display currency cannot silently alter the economic interpretation of existing trades. Failure to save retains inputs and shows recovery. Changing a default timeframe visibly affects the next relevant chart/run, or the setting is labeled as a future preference.

5. Combined analytics scopes are surprising and need an evidence-first hierarchy

Evidence: deselecting all profile IDs falls back to all available profiles (frontend/src/pages/workspace/CombinedLiveAnalytics.tsx:237–241). The 1W/1M/3M cutoff anchors to the latest closed trade, not today (:263–275); stale history can therefore appear to be a recent period. Default ranking is Score (:215, :298) and the view includes large metric/leaderboard families before the underlying trade table (:490–543, :625). The main profile comparison table has minimum width 1180px and horizontal scrolling (:626–627). Currency grouping is a strength: accounts are scoped by currency rather than summing incompatible currencies (:229–236).

Recommendation: show explicit date range and timezone, allow a true no-profiles-selected state, and distinguish Latest recorded period from Last calendar week/month. Start with scope, sample size, source completeness and net results, then drill into strategy/account decisions. Make mobile default to a compact profile list with expandable details rather than requiring repeated wide-table panning. Keep currency separation.

Acceptance: unchecking all profiles clears the results; Last week uses the documented calendar/rolling definition; every breakdown respects the displayed scope. A 360px viewport supports review of one profile/trade without losing its identifying labels.

Proposed wireframe/navigation

Global chrome: Workspace · Data Library · Tools, with Account/Settings in a secondary menu. Automation is a Tools capability, not a forced first-use destination.

Workspace first paint: resume recent work; Import trades / Start practice / Open chart; then profiles and an Unreviewed queue. Show one next useful action for each profile. Suppress dense empty analytics until records exist, while explaining what will be measured.

Inside a verified profile: persistent profile selector and context; Overview · Journal · Chart · Practice (where appropriate) · Connections · Settings. The header has a textual Read only / Paper / Historical practice / Broker execution mode and separate source/account selectors. Chart, journal review and practice links preserve this context.

Journal-first entry: choose/import account identity → import preview or manual entry → reconcile → open trade review → see measured patterns. History charts are optional context, not a prerequisite for getting value.

Practice-first entry: choose project/question → choose validated dataset → set run assumptions → start → resume/finish → journal review. Missing data leads to Data Library with a return link to this run.

Accessibility and responsive strengths to preserve

  • Mobile navigation already uses visible labels, 44px minimum targets and aria-current (frontend/src/components/layout/MobileBottomNav.tsx:21–29).
  • Profile creation uses fieldsets/legends, labeled inputs and aria-pressed state on choices (TraderWorkspace.tsx:524–530). Wizard progress marks the active step with aria-current="step" (:507).
  • Profile tabs are links in a named navigation region (frontend/src/pages/workspace/ProfileShell.tsx:117); page titles cover nested profile routes (frontend/src/hooks/usePageTitle.ts:83–87).
  • Responsive grids exist throughout Workspace and combined analytics. Preserve them while reducing first-use metric density. Keyboard focus, dialog return focus, screen-reader chart alternatives and real mobile chart usability require runtime verification; source classes alone do not certify them.

Validation boundary

No automated tests or user-session mutations were performed for this specialist review. Recommended end-to-end checks: clean local user journal journey; valid candle import to historical chart without broker; missing-source recovery with return path; keyboard-only creation/review; currency-change behavior with existing records; deselect-all analytics; profile settings persistence failure; 360px and wide-screen navigation continuity.

Strike Profile is a strike/expiry exposure view. These are model-derived exposures, not direct observation of every dealer's position. The sign convention, units, inputs and approximation should be visible in the analytical explanation.
  • Straddle family: Straddle Chart fetches broker-backed series (blueprints/straddle_chart.py:20–30); Straddle PnL has a separate simulation endpoint (blueprints/custom_straddle.py:21–33). Do not confuse an automatic straddle-adjustment simulation with a generic replay paper account. Keep its entry/cost/adjustment assumptions attached to its output.
  • Arbitrage: explicitly NFO/MCX universe (frontend/src/pages/Arbitrage.tsx:191, :428), with a real basket-order call (:398). That is executable specialist functionality, not harmless journal analysis. A two-leg basket should show each leg's actual outcome and resulting residual exposure; a spread opportunity does not establish atomic fill certainty.
  • Strategy Builder / Portfolio: real broker chain/expiry/margin/quote integrations, normalized saved identity hydration and an execution dialog (frontend/src/pages/StrategyBuilder.tsx:120–132, :699–705, :1174–1278, :1613–1654, :1868). Saved leg snapshots are server-persisted as JSON in strategy portfolio storage (database/strategy_portfolio_db.py:43–52, :113–159). Portfolio has MyTrades and Simulation watchlists, not profile practice-run ledgers (frontend/src/api/strategy-portfolio.ts:3; StrategyPortfolio.tsx:287–319). A saved simulated option basket is distinct from a replay run and distinct from verified fills.

Five workflow priorities

1. Local historical research is unnecessarily coupled to trading access

Even after selecting local history, the portfolio/SIP frontend requires an API key (PortfolioBacktester.tsx:174–176; SipBacktester.tsx:85–87). Routes also sit behind broker-gated Layout (frontend/src/App.tsx:215 and frontend/src/components/layout/Layout.tsx:13–22). Backend does support choosing local data separately (portfolio/data.py:328).

Separate local-app authentication from broker connection. Data-library research should require a usable dataset, not an execution account. Retain broker requirements only for operations that genuinely need account data or live provider calls. API authentication alone is not inherently a paid-data dependency; explain those separately.

2. The catalogue leads with automation rather than the core user job

frontend/src/pages/Tools.tsx:68 orders Automate before Core trading and Options Lab. Its first description says “Start here when you want Chartly to act for you” (:13). Meanwhile the product's desired first outcome is journaling, chart study or practice.

Use “Research” as supporting navigation with tasks: Compare allocations, Inspect options, Build a strategy. Put automation in an explicit advanced area. Keep existing specialist routes, but each tool entry should explain market support, required source and whether it can submit orders. Capability matching should determine availability, not a blanket “tools available” count.

3. Tools do not carry research context back to the core journal

Searches across portfolio results/analyzer, Strategy Builder/Portfolio and GEX found no traderDb, profileId, runId or journal handoff. Strategy Portfolio separately stores scenario snapshots; the journal uses another model. Users must mentally reconnect research, decisions and outcomes.

Add “Save research to profile” and “Attach to trade” using immutable evidence snapshots: instrument/expiry, source timestamp, model settings, scenario legs, intended risk and rationale. A hypothetical output must remain labeled research; a MyTrades watchlist entry is not automatically a verified broker execution. Only normalized execution events create factual fills.

4. Research results need durable experiment identity and reproducibility

Portfolio and SIP stores explicitly retain only the latest result in memory (frontend/src/stores/portfolioBacktestStore.ts:4–8, :17; sipBacktestStore.ts:4–8, :17). The anti-staleness motivation is sound, but refresh destroys the current experiment and a direct result link cannot recover it.

Persist an explicitly dated experiment containing inputs, dataset version, engine/model version and results. Display the saved run's time and coverage rather than silently refreshing its interpretation. Allow Compare runs and Attach research. Keep backtests separate from live account equity.

5. Shared capability and analytical state should replace repeated defaults

frontend/src/hooks/useSupportedExchanges.ts:36–39 falls back to a broad venue set while capabilities load, and :105–109 chooses NFO/NSE defaults even if no appropriate venue exists. Each options page separately resets underlying/expiry and handles discovery; e.g. GEX retains defaults on underlying-fetch failure (GEXDashboard.tsx:86–117) and clears expiry failures without a persistent explanation (:123–149).

Use a shared research context: source/account, eligible instrument, expiry, snapshot freshness and capability reason. Distinguish “loading capabilities” from “no supported market”; show a recovery action for expired login, unavailable chain or missing OI. Do not present assumed defaults as discovered provider support. Each computed panel should identify inputs and limitations; a model with invalid premiums should not appear as an authoritative market fact merely because a curve can be drawn.

Proposed supporting research journey

Profile or journal review → choose research question → select eligible source/dataset → inspect coverage/model assumptions → run research → save dated experiment → attach rationale and chart evidence to a planned trade or practice goal → execute in an explicit mode → import/reconcile actual outcomes → review the original hypothesis.

Wireframe: one scope strip (profile, source, instrument, expiry/date); one principal research view; an adjacent Interpretation/Notes area; one Save research action. Execution is a separate explicit ticket. Advanced numeric controls remain expandable. Options pages can retain separate deep links while sharing scope and saved evidence.

Acceptance gates

  1. A user with local equity history can run supported portfolio/SIP research without connecting a live broker, with missing data clearly listed.
  2. A broker with no eligible option venue sees a clear unavailable state rather than a default NFO request.
  3. Saving and reopening an experiment restores exact assumptions, dataset identity and results.
  4. Research attaches to the selected profile/trade without becoming a factual fill.
  5. Every execution-capable research tool identifies mode and destination, and reports per-leg outcomes.
  6. Market-specific labels and models remain explicit; global support is not inferred from a generic tool title.

Audit 09 — Automation, AI and operational workflows

Date: 2 November 2026. Method: bounded read-only source inspection. No workflows activated, scripts run, keys accessed, orders submitted or settings changed. No live-provider or end-to-end automation certification is implied.

Assessment

Chartly contains substantial advanced automation and operational engineering. These surfaces serve a trader who already has a verified execution connection and wants repeatable execution or diagnostics. They should support the journal/chart/practice product, rather than define the first-run experience. The biggest integration issue is that automation runs in the older user/API-key/broker context, while the new profiles, destinations and local journal form a separate product model.

Section coverage

  • Flow: visual editor, saved workflows, activation, trigger registration, execution status, approvals and execution logs. Source reviewed: frontend/src/pages/flow/FlowIndex.tsx, FlowEditor.tsx, blueprints/flow.py, database/flow_db.py, services/flow_executor_service.py.
  • Python strategies: separate process host, scheduling, stop/start/deletion concurrency controls, logs, shutdown/restore handling. Source reviewed: blueprints/python_strategy.py and frontend index/scheduling references. This is user-code hosting, not an isolated historical paper-trading simulator.
  • Strategy module: guided strategies, runtime controls and execution lifecycle. Detailed fill/recovery assessment belongs to audit 06; these existing mechanisms should be reused rather than replaced by another independent order engine.
  • Platforms and Chartink: external alert/webhook configuration for TradingView, GoCharting and Chartink. These are alert-trigger integrations, distinct from an MT5/NinjaTrader local data/execution bridge (frontend/src/pages/Platforms.tsx:10–35, :92–96).
  • AI Agent: optional model/provider setup, Chartly tool key, conversation surface, explicit trading capability and confirmation flows. Source reviewed: frontend/src/pages/agent/AgentIndex.tsx, AgentChat.tsx, components/agent/AgentSetupGate.tsx, blueprints/agent.py.
  • API access and Action Center: global auto/semi-auto execution mode, pending approvals and broker-response state. Source reviewed: frontend/src/pages/ApiKey.tsx, ActionCenter.tsx, blueprints/apikey.py, database/action_center_db.py, services/action_center_service.py.
  • Operations: Admin routes cover freeze quantities, calendars, sessions, security, traffic, latency, diagnostics, model configuration and remote MCP. Logs and Health monitor provide deeper system observations (frontend/src/pages/admin/AdminIndex.tsx:36–110, pages/LogsIndex.tsx, pages/HealthMonitor.tsx). These are maintenance surfaces, not evidence that profile connectors have measured health.

Five priorities

1. Automation execution identity is separate from trading profile identity

Evidence: blueprints/flow.py:28–33 resolves the API key from the current session username; activation obtains that key (:526, :582, :608) and trigger registration receives it. Flow execution constructs the client using the key (services/flow_executor_service.py:4974–4977). Its market subscription owner resolves username/broker from the same credential (:369–377). No profileId/portfolioId reference was found in the inspected Flow, Python-strategy, Agent or Chartink page families or Flow blueprint.

Impact: the user may enter automation from a profile-led product and assume the selected profile's sources, copy destinations and drawdown settings apply. The inspected execution path does not establish that relationship. This is a scope/contract gap, not proof of an authorization vulnerability.

Recommendation: every executable automation has a verified execution binding: profile, account, instrument mapping, environment, allowed capabilities and version. Display it on the workflow card, editor header, run preview, approvals and activity. A workflow without binding remains a draft. Keep legacy automation explicitly labeled until migrated.

Acceptance: moving between profiles never silently changes an activated workflow's account. A run's account can be traced from trigger through command, broker response and journal event. Disabled/unavailable bindings block submission with a recovery action.

2. Execution permission is fragmented across global API mode, workflow state and AI settings

Evidence: frontend/src/pages/ApiKey.tsx:49 initializes the mode as auto, and blueprints/apikey.py:54 also falls back to auto. The API page explains that Semi-Auto queues API orders for manual approval (ApiKey.tsx:203–204). Flow activation is a separate action (FlowIndex.tsx:88–103). AI configuration independently defaults trading disabled (AgentSetupGate.tsx:58); AI chat passes its setting (AgentChat.tsx:111) and handles confirmation frames (:119–126). Backend capability code explicitly narrows the request against server policy (blueprints/agent.py:2300, :2354–2367).

Impact: “off”, “manual”, “semi-auto”, “analyze” and “approval” can mean different things in different surfaces. New users should not have to infer whether a saved workflow may submit immediately from a setting on a developer key page.

Recommendation: one visible execution summary, with distinct concepts: Read-only / Simulation / Broker execution; Draft / Armed; Approval required / Automatic. Keep backend checks authoritative and preserve AI confirmation controls. Put the relevant current policy beside the activation action; show exactly which routes it covers. Prefer preview/demo-first onboarding before automatic execution.

Acceptance: activation preview shows destination, permissions, approval policy, schedule and order limits; AI trading disabled prevents execution regardless of prompt; historical practice cannot reach these live endpoints. Do not claim the global Semi-Auto switch governs arbitrary Python code unless enforced by its actual execution path.

3. Approval, submission and fill need one consistent activity vocabulary

Existing strength: Action Center explicitly models an approved-but-unconfirmed send (ActionCenter.tsx:78–110). Its timeout is an investigation prompt, not proof that submission failed. database/action_center_db.py:284–306 uses a conditional claim so only one caller sends an approved order; :323–359 returns an approval to pending only under specified never-sent conditions. The page tells the user to inspect the broker book rather than duplicate an unknown order (ActionCenter.tsx:750). Preserve this careful behavior.

Gap: the page still has fallback success copy “Order approved and executed” (ActionCenter.tsx:285) and top-level tabs/statistics group by approval state (:521–525, :563), while actual broker state is separate. Approval is not proof of a fill.

Recommendation: activity timeline is Trigger received → Validated → Awaiting approval → Claimed → Submitted → Acknowledged → Partially filled / Filled / Rejected / Cancelled / Unknown. The user can filter by run/decision/account and open the same event from Flow, Agent and Journal. Avoid a generic retry button for uncertain submissions.

Acceptance: a broker response timeout remains Unknown without duplicate submission; one approval produces at most one claim; a rejection is never shown as completed trading; partial fills remain visible until reconciled. Test ambiguous failure and reconnect paths, not just success.

4. Scheduling and logs retain regional assumptions

Evidence: blueprints/python_strategy.py:64 defines Asia/Kolkata; scheduler initialization uses IST (:312–325) and timestamps/log names use it (:564–580, :823–825). Action Center exposes created_at_ist and approved_at_ist (ActionCenter.tsx:65; services/action_center_service.py:53). Admin's initial cards are oriented to F&O freeze quantities and a seven-exchange timing catalogue (AdminIndex.tsx:36–62).

Impact: global FX/futures users may misread run and approval time, especially around daylight-saving transitions, unless the timezone is explicit. A profile timezone does not automatically control these older services.

Recommendation: persist UTC event times and an explicit schedule timezone/calendar; display profile timezone with an exchange-time alternative. Show next scheduled execution as a concrete date/time/zone before arming, including missed-run behavior. Keep regional features as optional market-specific capabilities.

Acceptance: a London schedule remains tied to London wall time across DST; UTC logs preserve event order; missing holidays/calendar data is visible; late start and stop policies are documented and tested.

5. Advanced setup and diagnostics should be contextual and optional

Evidence: Agent setup requires a tested model and a Chartly API key (AgentSetupGate.tsx:30–32, :82–95); its copy supports a local provider and encrypted storage. AgentIndex.tsx:61–92 shares a setup gate and loading state across surfaces. Platform webhooks require API-key setup (Platforms.tsx:92–96). Admin includes Agent Config and remote MCP (AdminIndex.tsx:97–110); logs separately expose health, traffic, security and latency (LogsIndex.tsx).

Impact: these are valid advanced jobs, but they can make free journaling look like it requires an AI subscription, API setup or server operation. A configured AI model should remain optional; failed configuration checks should not be mistaken for proof that no model exists (AgentIndex.tsx:16–18 describes that choice).

Recommendation: Tools → Automate contains Flow, scripts, alert integrations and Approvals. Settings → Advanced contains API access, AI providers, system logs and remote MCP. Show a concise prerequisite list on each tool before setup. A chart/journal error opens a targeted diagnostic view already scoped to the failing subsystem. For AI, show configured-but-unreachable separately from unconfigured, and preserve read-only mode by default.

Acceptance: journal, dataset import and practice can be completed with AI unconfigured; credentials are never required merely to inspect local notes. A failed automation links to its run log, source and execution binding; a support export previews/redacts sensitive material rather than making users copy raw logs.

Existing engineering to preserve

  • Flow keys are encrypted in storage and decrypted through a helper (database/flow_db.py:59–77, :96, :266–268). This source fact does not certify the whole key lifecycle.
  • Python host has explicit process and restore concurrency controls, shutdown refusal and durable running-state handling (blueprints/python_strategy.py:67–118); scheduling bounds late jobs rather than silently treating all misfires the same (:255–268).
  • Flow records last execution state and links approvals from its own hub (FlowIndex.tsx:282–286, :661–683).
  • Action Center preserves ambiguous submission state and has a conditional execution claim.
  • AI server ownership checks return indistinguishable not-found responses for unavailable conversations (blueprints/agent.py:14, :302); approval decisions are recorded before run resume (:2869). These are useful patterns to extend to normalized profile/run events.
  • Diagnostics and health surfaces already exist. Build product recovery entry points to them rather than another monitoring dashboard.

Target wireframe journey

  1. Choose Automate from an existing verified account/profile context.
  2. Choose Visual workflow, Script, External alert or AI assistance; show prerequisites and current permissions.
  3. Draft logic with a persistent header: profile, account, environment and approval policy.
  4. Validate and inspect a dry-run/preview with normalized orders and expected limitations.
  5. Arm explicitly; display trigger, next schedule, allowed scope and stop behavior.
  6. Inspect one activity timeline. Pending approvals show exact account and command; uncertain sends link to reconciliation.
  7. Stop automation independently of closing positions; make that distinction explicit.
  8. Reconcile fills into the journal, then review strategy execution against intent.

These are proposed requirements. The complete profile-scoped automation-to-journal journey was not found or executed in this bounded review.

Audit 10 — Open-source and local-first maintenance readiness

Reviewed 2 November 2026. Read-only source inspection of this checkout, not a public-upstream audit, legal opinion or security certification. No application code, credentials or user data changed. No additional tests were run by this reviewer.

Assessment

The app has serious maintenance foundations: pinned dependency manifests, multi-version CI, frontend tests/builds, backend smoke checks, Docker persistence and detailed subsystem documentation. The free local journal/chart/replay product needs a smaller, tested entry path and clearer release contract. Current installation, storage, documentation and integration boundaries still reflect a larger broker-automation server.

Five priority findings

1. This checkout does not establish a complete open-source distribution contract

The root directory contains no LICENSE, README, CONTRIBUTING or SECURITY file. This is an absence observed in this supplied checkout, not proof that upstream lacks them. pyproject.toml:1–5 defines project identity and Python requirement but no project license declaration. The frontend uses registry aliases chartly-charts → openalgo-charts@2.6.7 and chartly-script → openalgo-script@0.8.1 (frontend/package.json:55–57); the installed packages declare Apache-2.0 in their manifests. Those dependency declarations do not define the license of the host application or replace the need to preserve applicable notices.

Before distributing: provide an authoritative host-app license, attribution/notices inventory, contribution instructions, support scope and vulnerability-reporting contact; verify the actual distribution contents and retained notices. Avoid presenting rename/alias work as ownership of upstream components. Retain the dependency version/integrity information already in frontend/package-lock.json:6900–6913.

2. Installation guidance does not lead the local no-broker user to first value

install/README.md:7–15 lists Linux prerequisites, :17 labels domain/DNS setup required and :42 labels broker setup required. The download examples around :64–76 contain bare wget and curl -O without a URL. These instructions are unsuitable as the front door for a Windows journal user with a CSV and no broker. This does not mean all installation documentation is cloud-only: DOCKER_README.md includes Windows instructions and loopback endpoints. The problem is fragmented entry guidance and required-versus-optional scope.

The parent observed that noninteractive .venv/Scripts/python.exe app.py raised the Werkzeug production guard, while starting it with a PTY served successfully. The source launch is app.py:1088–1090, :1245. Treat this as a documented local-launch requirement to resolve, not a reason to weaken production guards. Provide one supported Windows/local launcher, a local Docker route, an optional development route and a separate server deployment guide. Local start must not imply that broker connectivity, MT5 or native bridges have been verified.

Acceptance: a clean supported Windows machine can install, start, stop and reopen the app; add/import journal records; import a historical dataset; and preserve work without a domain, Cloudflare account or broker credentials. Record tested OS/runtime versions and known limitations.

3. “Back up the app” is currently several different storage tasks

The journal uses browser IndexedDB (frontend/src/lib/trader/db.ts:209) while .sample.env:54–61 declares multiple SQLite files plus Historify DuckDB. docker-compose.yaml:14–20 persists backend db/log/strategy/key/tmp paths in volumes, but that cannot back up the browser journal. frontend/src/pages/workspace/TraderJournal.tsx:321–363 exports selected CSV columns, not full journal/profile/review state. Existing chart workspace import/export is another separate mechanism.

A credible local-first release needs a storage inventory visible to the user and one complete, versioned recovery workflow. Define what is browser-local versus backend-local, which host/port/browser identity owns it, and how to move between machines or browsers. An update must not silently appear to erase a journal because the app origin changed. Back up database relations, chart state, profiles, attachments, practice checkpoints and dataset provenance; keep secrets appropriately separated. Test restore into a clean installation, not only creation of an archive.

4. CI breadth is stronger than current product-journey assurance

CI has backend tests across Python 3.12–3.14 (.github/workflows/ci.yml:37 onward), real server boot smoke stages, frontend build on supported Node majors (:362 onward), frontend unit/coverage tests (:388–411) and Chromium E2E (:417–437). Preserve these strengths. Backend lint/format steps are advisory via continue-on-error (:30, :33), as are security-scan commands (:452, :455), so green CI must not be described as every finding being resolved.

The E2E harness starts Vite only (frontend/playwright.config.ts:64–70), whose API/auth routes proxy to localhost:5000 (frontend/vite.config.ts:35–54). The E2E CI job shown installs npm/browser and runs tests but does not start the Flask backend in that job. Some tests accept minimal body visibility or conditionally skip a login action if absent (frontend/e2e/home.spec.ts:6–35); navigation tests can accept the login form rather than the authenticated destination (frontend/e2e/navigation.spec.ts:25–58). These are useful smoke checks but cannot establish import → chart → replay → journal → restore behavior.

Add deterministic full-stack fixtures and a few decisive journeys: fresh no-broker user, journal edit/import/deduplication, local-history access, replay resume and automatic journaling, backup/restore, and execution isolation. Keep live broker certification separate from normal CI and require sandbox/adapter contract fixtures for connector releases. Parent/specialist unit passes remain scoped evidence, not general product certification.

5. Dependency and documentation boundaries need an owned capability matrix

frontend/vendor/README.md:3 describes chart dependency 2.4.5, while the manifest/lock/install resolve 2.6.7. The vendor document correctly warns that package availability does not imply every host control is integrated (:14–17); preserve that distinction but generate version/capability references from the shipped build. The frontend also includes a local chartly: file:.. dependency (frontend/package.json:55) and both frontend and Python components participate in the strategy-language stack. These cross-runtime and vendor boundaries need explicit compatibility/upgrade ownership.

Keep a small capability matrix identifying each surface as implemented, configuration-only, experimental or connector-dependent; distinguish upstream engine support from Chartly host integration. Include version compatibility, supported account/asset classes, dataset requirements, how to reproduce regressions and who owns each adapter. Use the current report's findings to replace architecture promises with demonstrable supported paths. No market-size, platform availability or regulatory claim in architecture prose should substitute for current vendor evidence or specialist advice.

Maintenance strategy

Maintain a stable local core: normalized journal, durable data/run models, read-only chart sources, simulator, import/export/recovery and a small number of complete journeys. Treat broker adapters, automation, options labs and terminal bridges as capability-scoped extensions. Preserve advanced work rather than deleting it, but avoid forcing every new user and contributor to understand it before improving the journal. Each connector multiplies auth, symbol, unit, market-hours, restart and order-state cases; increase coverage only after the contract is testable.

Release gates for the free core

  • Distribution includes a clear host license, applicable notices and reproducible versioned source/build instructions.
  • A clean local supported installation reaches journal and imported-history charting without a paid provider or execution broker.
  • Journal corrections, imports and recovery preserve IDs, notes, provenance and relationships.
  • Dataset versions and replay assumptions make results reproducible; replay orders cannot reach real broker routes.
  • A saved run resumes after process/browser restart and automatically produces a reviewable journal record.
  • Update/migration and complete restore are exercised on a clean machine/profile.
  • Docs identify supported, incomplete and experimental functions accurately; configuration state never claims actual connectivity.
  • Startup/stop, local storage, resource limits and failure recovery have actionable user-facing states rather than requiring log archaeology.

These gates describe observable behavior, not a request to delay local reversible development or add approval bureaucracy. No release timeline is estimated here.
