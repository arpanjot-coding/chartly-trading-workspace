## Problem and intended flow

The current app exposes an app-wide legacy broker login (defaulting to Zerodha), a separate verified connection registry, saved profile configuration, and a separate local-data proof. These compete in the same user journey. Local mode promises account-free use but cannot import durable history. Live profile creation offers irrelevant simulator/setup radio choices. Developer tools expose global sandbox-routing and appearance locks as if they were workspace trading modes.

The intended flow is: open the personal app → use local chart/journal/imports → optionally connect a brokerage, crypto exchange or desktop platform → observe its actual account and supported data → associate the appropriate profile/book. Connecting a source, importing saved history and choosing an execution account are separate purposes. Provider credentials are requested only for the provider capability that needs them. Developer API remains a separate integration tool.

## Frozen UI/catalog contract

Catalog entries add `category: brokerage | crypto | desktop | diagnostic`, `connectionMode: account | public-data | diagnostic`, and `setupState: available | prerequisites | planned`. Existing provider IDs and measured capabilities retain their meanings. A public-data connection must never be presented as a brokerage account or produce an account journal. Unimplemented providers have no functioning Connect claim. Source selection is user intent; observed identity/permissions/coverage are facts.

The UI uses the catalog rather than guessing categories from names. Existing MT5 read-only and diagnostic behavior remains compatible. Kraken public time reachability alone is not market-data support; the W07 source must pass its own tests and review before its action becomes available.
